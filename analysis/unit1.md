# Modeling Justification, 400 to 600 words
The relational design for the Cargo van rental marketplace uses five relations(tables).  The five tables area renters, viewings, properties, listing_amenities, and amenities.  The renters represent all customers that are looking to rent a cargo van for any use.  The properties relation is the vehicle listing of all cargo vans.  The viewings relation handles all the measurement metric and are the foreign keys to each renters relation and properties relation its the high volume fact table recording each action; timestamp and viewing duration by customers.  The amenities relation encases all features a cargo van or property may have inside it such as; high roof, lighting on the inside, GPS, Siri, cargo shelves, and backup camera.  Lastly, the listing_amenities relation connects both properties and amenities relations.  

I used IDs for four of the relations (renters, viewings, properties, and amenities) to keep it simple and quick, such as being able to query each piece from each relation.  This made it unique by each numeric number established at the start. For example renters may have the same name of "John Smith," and the ID would allow the query to find the correct one being used.  The same can be said for display_name of properties relation in which we can just query by the primary key on an ID.  The listing_amenities relation -Junction table uses the PK to distinguishes each property (vehicle) from whatever amenity it has installed, it can never be assigned to the same vehicle more than once.

Under the viewings relation the foreign key for both renter_id and property_id are restricted for deletion due to ever having any existing viewing by a renter (customer) or an property (vehicle) having an viewing by a customer.  If and when we need to analyze data for viewing purposes we can do so from either of these, as we cannot delete but we keep the data and can view duration or viewing of property and by whom. 

The modeling justification by this ERD design show all primary keys as unique, all foreign keys as either preventing any deletion of properties or renters and even assigning any amenities to any properties.  Many of the features of each relation cannot null and many must be greater than > 0 (zero).  The last two attributes daily_rate and duration_min show as greater than zero, never negative within this entity relational design.  These constraints are important as it protect the integrity of the relations within the database design.
